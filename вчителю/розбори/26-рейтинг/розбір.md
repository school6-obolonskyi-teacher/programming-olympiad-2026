# Розбір: 26. Рейтинг

Умова: [задачі/26-рейтинг/умова.md](../../../задачі/26-рейтинг/умова.md) · Тема: [сортування](../../../учням/теми/08-сортування.md)

## Ідея алгоритму

Треба відсортувати учасників за правилом з трьох ознак і вивести їхні номери. Номер — частина запису, тож кожного учасника зберігаємо трійкою `(s, t, номер)`.

Правило «хто вище» записуємо функцією-**компаратором**, яка перевіряє ознаки по черзі й повертає результат за першою, що відрізняється:

```cpp
// чи стоїть x у рейтингу вище за y?
if (x.s != y.s) return x.s > y.s;   // більше балів — вище
if (x.t != y.t) return x.t < y.t;   // менший штрафний час — вище
return x.id < y.id;                 // менший номер — вище
```

і передаємо її в `sort`. У Python замість компаратора задаємо **ключ** — кортеж `(-s, t, номер)`. Кортежі порівнюються так само: спершу перші елементи, за рівності — другі, потім треті. Мінус перед `s` перетворює «більше балів — раніше» на звичайне «менше — раніше», як і для двох інших ознак:

```python
order = sorted(range(n), key=lambda i: (-s[i], t[i], i))
```

Той самий прийом працює і в C++: можна сортувати `vector<tuple<int, int, int>>` з елементами `(-s, t, номер)` без власного компаратора.

## Обґрунтування правильності

**Рейтинг визначено однозначно.** Позначимо ключ учасника `i` як `k(i) = (−sᵢ, tᵢ, i)`. Учасник `x` стоїть вище за `y` тоді й лише тоді, коли `k(x) < k(y)` у лексикографічному порядку (по елементах зліва направо). Справді:

- якщо `s_x ≠ s_y`, усе вирішують перші елементи: `−s_x < −s_y` ⟺ `s_x > s_y` — правило 1;
- якщо `s_x = s_y`, але `t_x ≠ t_y`, вирішують другі: `t_x < t_y` — правило 2;
- якщо збігаються і бали, і час, вирішують номери — правило 3.

Номери різні, тому ключі двох різних учасників ніколи не рівні: будь-які двоє порівнянні, і рівно один із них вище. Отже, правильна відповідь єдина — це впорядкування ключів за зростанням. Будь-яке правильне сортування з таким порівнянням дає саме його. Тому задача не потребує чекера: відповідь учасника звіряють з еталонною число за числом.

**Чому важливий третій ключ.** `std::sort` у C++ **не стабільний**: учасники, для яких компаратор не бачить різниці, можуть опинитися в будь-якому порядку. Якщо компаратор порівнює лише `s` і `t`, порядок учасників з однаковими `(s, t)` стає довільним. На тесті 08 (20 однакових учасників) такий розв'язок вивів `11 20 19 … 12 1 10 9 … 2` замість `1 2 … 20`. Підступно те, що масиви до 16 елементів `std::sort` у GCC сортує вставками, а цей метод рівних не переставляє. Тому на прикладах з умови (`n ≤ 5`) помилка не видна, і її ловлять лише тести з десятками однакових учасників.

У Python `sort` і `sorted` **стабільні**, тож ключ `(-s, t)` без номера теж дає правильну відповідь: рівні учасники лишаються в порядку `range(n)`, тобто за зростанням номерів. Проте краще писати номер явно — так видно, що правило 3 враховано свідомо. У C++ аналог — `stable_sort` з компаратором за `s` і `t`.

**Чому компаратор має бути строгим.** `std::sort` вимагає від компаратора **строгого слабкого порядку**: зокрема, `comp(x, x)` має бути `false`, а з `comp(x, y)` має випливати `!comp(y, x)`. Компаратор з `>=` чи `<=` повертає `true` для двох однакових учасників, і ці вимоги порушено. Стандарт C++ у такому разі нічого не гарантує — це **невизначена поведінка**.

На практиці буває так. Під час розбиття масиву `std::sort` (GCC) рухає індекс уперед циклом «поки `comp(a[i], опорний)`» і **не перевіряє межу масиву**, щоб працювати швидше. Зупиняє цей цикл перший елемент, не менший за опорний, а такий завжди є: принаймні сам опорний, бо `comp(опорний, опорний)` має бути `false`. З `<=` цикл не зупиняється на рівних елементах і виходить за межі масиву. Ми перевірили це на розв'язку з `return a.t <= b.t` (без номера):

- на малих тестах (до 16 учасників) він виводить рівних учасників у зворотному порядку: приклад 2 дає `4 2 3 5 1` замість `2 4 3 1 5`;
- на тестах з багатьма однаковими учасниками (08, `s2-dup`, `s2-same`, `s2-high-t`, `b-dup`, `b-same`) програма завершується аварійно: на тесті 08 — з повідомленням `free(): invalid pointer`, тобто вона записала дані поза масивом.

Компіляція з `-D_GLIBCXX_DEBUG` ловить помилку вже на прикладі 2: `comparison doesn't meet irreflexive requirements, assert(!(a < a))`.

Якщо ж у компараторі є номер, то в перших двох рядках `>=` замість `>` нічого не змінює: туди потрапляють лише учасники з різними `s` (чи різними `t`). А от `x.id <= y.id` в останньому рядку формально знову порушує вимогу `comp(x, x) = false`. Тож звичку писати в компараторі лише `<` і `>` варто виробити одразу.

## Складність

- Час: O(n log n). При `n = 2·10⁵` це близько `2·10⁵ · log₂(2·10⁵) ≈ 3,6·10⁶` порівнянь.
- Пам'ять: O(n) — масив трійок.
- Тип даних: `tᵢ ≤ 10⁹ < 2³¹ − 1 ≈ 2,1·10⁹`, тому вистачає `int`. Якщо ж «склеювати» ознаки в одне число (наприклад, `(800 − s)·(10⁹ + 1) + t` — близько `8·10¹¹`), потрібен `long long`.
- Еталон на C++ працює до 0,12 с на найбільших тестах, на Python — від 0,45 до 0,66 с у різних запусках (WSL; більший час — коли комп'ютер був навантажений іншими процесами). Найдовше Python сортує тести з багатьма рівними балами (`b-ties`): там кортежі доводиться порівнювати до другого й третього елемента.

Квадратичне сортування (бульбашкою, вставками, вибором) при `n = 2·10⁵` робить близько `n²/2 = 2·10¹⁰` порівнянь — орієнтовно десятки секунд навіть на C++. У наших запусках бульбашку на кожному великому тесті довелося зупиняти примусово через 5 с. При `n = 1000` порівнянь лише `5·10⁵`, і бульбашка навіть на Python працює до 0,31 с, тож підзадачі 1 і 2 вона проходить.

Чому всі помилки в правилі порівняння набирають саме 20 балів: у підзадачі 1 бали різні, тож друге й третє правила не застосовуються ні разу. Що б розв'язок не робив з часом і номерами, він упорядкує учасників правильно, якщо правильно впорядковує бали. Підзадача 2 відрізняє тих, хто реалізував усі три правила, а підзадача 3 — тих, хто сортує за O(n log n).

Подробиці щодо швидкості:

- `cmp_to_key` у Python викликає функцію-компаратор на кожне з мільйонів порівнянь: 1,30–1,46 с на тестах `b-rand`, `b-ties`, `b-high-t`, `b-zero`.
- `input()` у циклі дав 1,20 с на одному тесті (`b-high-t`), решту великих тестів пройшов. Це межа, і на іншому комп'ютері результат може бути й 100, і 50 балів. Тому швидке читання через `sys.stdin.buffer` варто вважати обов'язковим.
- Найшвидші варіанти на Python — два стабільні сортування (до 0,38 с) і «склеєний» ключ (до 0,46 с). У них сортуються окремі цілі числа, а не кортежі. Як еталон ми все ж залишили ключ-кортеж: він найближчий до умови і його найлегше перевірити очима.
- Сортування вставками встигає на `b-same` і `b-sorted` (вхід уже впорядкований, і жоден елемент не зсувається), але не встигає на решті шести великих тестів.

Усі результати отримано запуском `інструменти/перевірити.py` на відповідних розв'язках.

## Методичні примітки

1. Почніть з того, як складають справжні таблиці результатів: на Всеукраїнській олімпіаді рахують лише бали, на командних змаганнях ICPC — кількість задач і штрафний час. Нехай учні спершу на папері розставлять учасників прикладу 2 і проговорять, яке правило спрацювало для кожної пари.
2. Запишіть компаратор на дошці як три рядки `if … return …` і підкресліть: кожен рядок відповідає одному правилу умови, і кожен повертає результат, щойно ознаки відрізняються. Потім покажіть ту саму думку в Python: кортеж `(-s, t, i)` і мінус як спосіб «перевернути» лише одну ознаку. Корисно окремо показати, чому `reverse=True` тут не годиться (див. таблицю помилок).
3. Дайте учням здати розв'язок на C++ з `sort` без третього ключа. Він пройде всі приклади й набере лише 20 балів. Це найкращий привід поговорити про **стабільність** сортування: `sort` у C++ нестабільний, `stable_sort` і `sorted` у Python — стабільні. Розкажіть, чому малі тести помилку не показують (масиви до 16 елементів GCC сортує вставками).
4. Покажіть компаратор з `<=`: на прикладі 2 він тихо дає неправильну відповідь, на тесті 08 програма падає, а з `-D_GLIBCXX_DEBUG` g++ сам називає причину. Учні мають запам'ятати: компаратор для однакових елементів повертає `false`.
5. Порівняйте швидкість: бульбашка (50 балів), `cmp_to_key` у Python (50 балів), стандартне сортування з ключем (100 балів). Оцінку `n²/2 = 2·10¹⁰` проти `n log₂ n ≈ 3,6·10⁶` учні мають зробити самі ще до запуску.
6. Продовження: два стабільні сортування «спершу за менш важливою ознакою, потім за головною». Нехай учні пояснять, чому порядок саме такий і чому без стабільності прийом не працює. Оскільки `sᵢ ≤ 800`, можна обговорити й сортування підрахунком за балами ([тема 08](../../../учням/теми/08-сортування.md)). Задача Timus 1100 «Final Standings» вимагає саме стабільного сортування, а Codeforces 166A «Rank List» додає поняття «спільного місця» для повністю однакових учасників.
